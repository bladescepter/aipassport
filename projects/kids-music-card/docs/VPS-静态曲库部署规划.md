# VPS 静态曲库部署规划

> 用户指定使用现有 VPS。本文是待审核的部署方案，不是已部署状态。
> 配套设备需求见 [在线播放与离线收藏实施方案](在线播放与离线收藏实施方案.md)。本轮只读检查，未修改 DNS、Caddy、容器、防火墙或服务器文件。

## 1. 已核实的环境

依据本机综合助手项目的 `VPS-运维知识库.md`，并通过 SSH 只读复核：

- 腾讯云香港 Ubuntu VPS；运行 Docker、Caddy 和多个现有站点。
- Caddy 实际版本 **2.11.4**。现容器标签是 `caddy:latest`，但部署时必须记录并复用当前实际镜像 ID/digest，不能借新增站点升级到另一个 latest。
- 当次检查：约 3.6 GiB 内存、可用约 1.8 GiB；根盘约 69 GB、剩余约 35 GB。只是快照，不是持续保障。
- Caddy 网络 `hermes-net`，明确设置固定 IP **172.18.0.6**。现有 pi-web 防火墙依赖此地址，重建时不能丢失。
- 宿主配置：`/home/ubuntu/caddy/Caddyfile`，单文件只读挂载到容器 `/etc/caddy/Caddyfile`。
- 现有内容挂载：博客 `/blog` 和用量页 `/llm-usage`；另有持久卷 `caddy_data`。**没有音乐数据挂载**。
- `/opt/data/kids-music/` 在检查时不存在。

因此，不能只加 Caddyfile 并 reload 就宣称可提供音乐文件：新增挂载需要按正式部署定义受控重建 Caddy。必须保留其固定 IP、全部既有挂载、端口、资源限制、重启策略及数据卷，重建后验收全部原站点。

## 2. 推荐架构

```text
本机有权使用的音源
    → 本机编码裸 Opus、生成目录/哈希、字形与大小检查
    → SSH/SFTP 上传到 VPS 暂存区
    → 校验并发布只读版本化曲库
    → 现有 Caddy：HTTPS + 每设备只读 Basic Auth + 静态文件
    → ESP32-C3：分页浏览、流播放、最多 5 首持久缓存
```

首版不新建数据库、音乐服务器或上传 API，不在 VPS 转码；不把管理界面权限交给设备。缓存选择及音量/模式只存设备。在线播放约 4100 B/s，即约 14.8 MB/小时/设备，另有 TLS/网络开销；套餐带宽、流量和设备所在地到香港线路仍需核实。

### 域名与 DNS（待确认）

用户暂定使用 **`kidmusic.xiyuan.wiki`**；设备端已按此默认源站实现。部署前查实际占用情况；本文不假定 DNS/Caddy 已配置，当前设备接口以 [曲库 API v1](曲库API-v1.md) 为准。

首轮建议 Cloudflare **DNS-only**，直接到 VPS 的既有 HTTPS 入口：

- 由 Caddy 获取公开可信证书，不把 Cloudflare Origin CA 证书当成设备默认可信证书。
- 不套用需要浏览器登录的 Cloudflare Access、JS Challenge 或验证码；ESP32 HTTP 客户端无法完成这种登录。
- 不经过额外 CDN 转换或缓存链路，先证明 Content-Length、Range 和字节内容正确。
- 现有其他域名的 CDN/Access 不变，只对新增音乐域名单独处理。
- HTTP 可由 Caddy 跳转到 HTTPS，但设备 profile 必须直接填 HTTPS，不能依赖重定向。

若后续需要 CDN，应作为独立变更，重新验证鉴权、缓存隔离、Content-Encoding、Range、证书与异常响应。DNS-only 会公开源站 IP，这是方案取舍；并非隐藏源站的方案。

### 数据与权限

建议宿主结构：

```text
/opt/data/kids-music/
  public/                         # 唯一挂载给 Caddy 的内容，只读
    v1/current.json
    v1/releases/<release_id>/...   # manifest 和分页目录
    v1/audio/<sha256>.opus         # 不可变的长度前缀裸 Opus
  incoming/                       # SSH 上传暂存，不在公开根目录
  backups/                        # 发布回滚，不在公开根目录
```

建议只读挂载 `/opt/data/kids-music/public:/kids-music:ro`。私有凭据文件、原始音源和部署备份不能放进 `public/`；禁止目录浏览，不放可指向私有目录的符号链接。上传账户与 Caddy 文件读取权限分离，设备没有任何写入服务器的能力。

### Caddy 站点职责（配置在执行前生成并审核）

新增独立站点，功能限定为：

1. `root` 指向 `/kids-music`。
2. `basic_auth` 覆盖整个站点，包括 current、目录页和音频，不只保护首页。
3. `file_server` 提供原文件；不启用 `browse`、`encode` 或 `precompressed`，不做路径/域名跳转。
4. 裸流建议使用 `application/octet-stream`，不声称其为普通 Ogg Opus；JSON 使用正常 JSON 类型。
5. 目录索引允许重新验证或禁缓存；不可变音频可供设备私有缓存。共享缓存不得绕过鉴权，不设置 public 缓存授权内容。
6. 只读协议允许 GET/HEAD，其余方法拒绝。私有日志不记录 Authorization、Cookie 或配置输入；不启用会输出凭据的调试日志。

Caddy 2.11.4 使用指令名 `basic_auth`，不使用旧名 `basicauth`。服务端使用 `caddy hash-password` 生成哈希，配置不放明文密码；实际凭据和哈希不提交 Git。设备必须持有对应只读密码，放在私有 NVS，不能通过 URL 参数传递。

P0 设备拒绝所有重定向，也拒绝 chunked、压缩与长度不符。使用完整文件路径，检查正常响应具备 Content-Length；对 Range 实测 206/Content-Range。不用硬编码或伪造响应长度来让校验通过。

官方参考：

- [basic_auth](https://caddyserver.com/docs/caddyfile/directives/basic_auth)：要求哈希密码、鉴权失败返回 401。
- [file_server](https://caddyserver.com/docs/caddyfile/directives/file_server)：静态文件/部分内容；默认可能对目录/尾斜线进行 canonical redirect，音频请求必须避开此类路径。

## 3. 分两步部署，不先开发整套曲库

### A. P0 单曲测试端点

- 先选择一首已有、用户有权使用的裸 Opus 文件，不重新编码或改音频参数。
- 为文件算 SHA-256，以 `/v1/audio/<sha256>.opus` 发布，记录精确 `size_bytes`。修改音频必须生成新的哈希路径。
- 只配置一台设备的只读身份并验收；此时不需要 `current.json`、分页发布工具或网页后台。
- 给设备安全写入 profile（Wi-Fi 与源站/路径/鉴权/大小）。不要求用户在对话中贴密码，不把凭据放入命令行历史或日志；采用经审核的本地私有输入通道。
- 原 NVS/Flash 已备份不代表可以随意整体替换 NVS；新配置写入须保留所有现有键，采用设备端按命名空间更新优先。若选整分区生成/写入方式，必须先核实并保留所有命名空间，单独确认覆盖范围，不能只复制目前看到的音量/模式来保证未来无数据丢失。
- 通过真实 HTTPS 流播放、暂停/停止/切歌、弱网恢复及 30 分钟测试，才算 P0 通过。

### B. P1/P2 正式曲库

- 实现独立正式发布工具，复用编码核心但解耦现有工具会更新本机目录的副作用。
- 生成 `current.json`、不可变 release/manifest、20 首初始分页和音频哈希索引；页面数量与字体边界验证见设备方案。
- 上传至 incoming，逐个验证大小、SHA-256 和目录引用，再发布 release，最后原子切换 current；保留上一版便于回滚。
- 新增歌曲只更新服务器目录，设备刷新即可发现，不需刷机；歌名字形须通过设备字体覆盖检查。
- 固件实现四项首页、前两项列表的随机入口、设备端跨页最多五首缓存与掉电恢复。不用 Caddy 动态处理设备收藏。
- 已缓存的旧版本或远程下架歌曲不由服务器自动删除；整理需设备用户确认。

## 4. 受控变更步骤

1. 确认域名、DNS-only 策略、测试歌曲与使用权，以及 Caddy 短暂停机窗口。
2. 再检查 VPS 状态及套餐流量；定位正式容器部署入口（Compose 或实际管理方式），记录当前镜像、挂载、静态 IP、端口、资源限制和重启策略，不打印环境变量值。
3. 在持久化宿主目录备份 Caddyfile、部署定义及必要回滚信息；确认备份可读，旧镜像保留。
4. 创建独立数据目录，上传并验收单曲，准备站点配置、设备身份和只读挂载。私有参数不进 Git。
5. 在变更前验证新配置；同时核实宿主 Caddyfile 和容器挂载文件内容一致。单文件 bind mount 的 inode 陷阱按运维知识库处理。
6. 用当前已部署镜像、原部署参数和固定 IP 重建 Caddy，新增只读音乐挂载；不 pull latest，不改 pi-web 防火墙，不打开额外公网端口。
7. 新域名解析与证书签发按受控顺序完成；从外部真实请求验收音乐站点和既有站点。
8. 失败时按原部署定义/配置回滚，保持静态 IP 与数据卷，保留新音频文件，不自动 prune 镜像或清空数据。

本轮仅规划，以上执行动作均须在具体配置及变更范围审核确认后进行。

## 5. 服务端验收清单

| 测试 | 必须结果 |
| --- | --- |
| 无鉴权请求每类文件 | 401，不是浏览器登录 302 或成功 200 |
| 错误/撤销身份 | 401，不泄露文件正文 |
| 正确鉴权整文件 GET | 200，准确 Content-Length，无编码/跳转；大小与哈希一致 |
| Range 从非帧边界请求 | 206，起点/终点/总长准确，正文逐字节对应原文件片段 |
| Range 越界 | 416，设备不死循环 |
| 不存在文件 | 404，无登录重定向或伪装成功 |
| 音频与分页路径 | 不发生内容压缩或 chunked 转换（当前 P0 音频要求 Content-Length） |
| TLS | 公开信任链、主机名、时间校验成功；到期续签机制有效 |
| 权限 | 无匿名上传，无目录浏览，私有暂存与备份不可访问 |
| 原服务回归 | 博客、pi-web、RSS、阅读器、文件服务、校对、OpenKB、用量页等按原鉴权状态正常 |
| 发布回滚 | current 可切回上一 release；旧资源仍在 |

## 6. 需要用户确定的事项

- 暂定使用 `kidmusic.xiyuan.wiki`；首轮是否采用 DNS-only，上线前再确认域名当前用途及部署授权。
- 是否批准按原参数受控重建 Caddy、增加只读挂载；执行前提供具体变更预览和回滚方案。
- 设备现有 6 首歌如何迁移到最多 5 首缓存集合：不自动删歌，先上传并验证来源，再由用户确认保留/移除和容量方案。
